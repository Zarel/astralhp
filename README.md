# AstralHP: Hypertext Preprocessor

Hey. Remember how easy it was to make websites with PHP? You'd upload
some files to a shared host and it would just run the PHP files and
statically serve the others.

AstralHP lets you do that, but with [Astro](https://astro.build/) instead.
It can even run alongside PHP, so you can migrate a site one page at a time.

## Getting started

Start with:

```sh
npx astralhp init
```

This will ask you some questions to get you started. The webroot (defaulting
to `www`) is the directory that Apache serves - for instance, `www/about.astro`
will become `https://example.com/about`.

The adapter you choose in init determines how you'll deploy:

- `apache-static` (the default) just doesn't support dynamic pages, and will
  show an error message if you try to use them.

- `apache-proxy` is an approach where you build, put the files in the Apache
  webroot, and then run `npx astralhp start`. Apache will serve static files,
  and then proxy dynamic pages to AstralHP. It's quite performant.

- `apache-cgi` is an approach where you build, put the files in the Apache
  webroot, and that's it. It's slower, but may be more suitable for shared
  hosts that don't let you run a persistent server.

- `node` means you don't use Apache at all, and just serve the site directly
  from Node.

Once you're done with init, put some files in your webroot. For instance,
`www/index.astro` with:

```html
<h1>Hello, world!</h1>
```

For a fuller example, look at [`example/`](example/).

You can test the server by using

```sh
npx astralhp dev
```

To deploy, you'll need to run the build script.

```sh
npx astralhp build
```

Ideally, you do this on your live server, the one that's running Apache.
But you could also copy your webroot directory over to your host.
Make sure to include `.htaccess` and `.caches/dist/`. Note that if you
have any dynamic pages with NPM package dependencies, those will need to
be installed on the server as well.

Then, if you're using `apache-proxy` or `node`, you'll also need to start
the server:

```sh
npx astralhp start
```

This server listens on `127.0.0.1:4321` by default. The port can be changed
in the `astralhp.mts` config file. For how to manage a running server, use
`npx astralhp help`. The relevant commands are `serve`, `reload`, `stop`,
and `status`.

## `.astro` files

AstralHP uses [the same `.astro` files as Astro](https://docs.astro.build/en/basics/astro-pages/#astro-pages).

The main difference is that AstralHP doesn't enforce the directory layout Astro
does; instead, it uses file extensions to distinguish between `src/pages/` and
`public/`.

## Configuration

AstralHP does not need a config file in `apache-static` mode (an empty
`.htaccess` file marks a directory as a webroot). Otherwise, it needs an
`astralhp.mts` file in the project root, which looks like this:

```ts
export const config: import("astralhp").Config = {
	webroot: "www",
	adapter: "apache-proxy",
	port: 9001,
};
```

See [`src/config.d.ts`](src/config.d.ts) for config documentation.

One config file can be used for multiple webroots. `webroot` can be
an array.

In this case, you'll need to pass a webroot to `npx astralhp dev <webroot>`.

`build`, `serve`, and `start` also accept a webroot. By default they use all
discovered webroots.

## Apache

Your Apache setup requires:

- Apache 2.4.53 or newer
- `mod_rewrite`
- `.htaccess` support (`FileInfo` overrides)
- The webroot to be the Apache `DocumentRoot`
- If using `apache-proxy`: `mod_proxy`, `mod_proxy_http`, and `mod_headers`.
- either `FollowSymLinks` or `SymLinksIfOwnerMatch`

(These are all default settings except `.htaccess` support, which is usually
enabled by shared hosts.)

### `.htaccess`

When targeting Apache, AstralHP will reserve a section of `.htaccess` for its
own use. The generated block is marked like this, and will be created if it
doesn't exist:

```apache
# ===== BEGIN ASTRALHP =====
# Generated by `astralhp build`. EDITS WILL BE OVERWRITTEN.
...
# ===== END ASTRALHP =====
```

AstralHP replaces only this block and preserves all configuration outside it.

You can read the block to see what it does (deny access to `.caches`, support
leaving off `.html`, etc).

When using `apache-proxy`, the configured `port` is used both when generating
the proxy configuration and starting AstralHP.

With multiple webroots, Apache sends its document root in a private request
header so a shared listener can select the correct webroot, and preserves the
original hostname so Astro sees the public URL. A `PORT` environment variable
overrides the configured port for both commands; when starting multiple
`apache-proxy` webroots, this places all of them on one shared listener:

```sh
PORT=9001 npx astralhp build
PORT=9001 npx astralhp start
```

### CGI on Apache

`apache-cgi` lets you run dynamic pages on shared hosts that don't let you run
a persistent server:

```ts
export const config: import("astralhp").Config = {
	webroot: "www",
	adapter: "apache-cgi",
	// Optional if bun is already on Apache's PATH:
	runtimePath: "/home/username/.bun/bin/bun",
};
```

Compatible with both Node and Bun, although we strongly recommend Bun because
startup times are important if you're going to spawn a new process on every
pageview.

Use a Node version that meets AstralHP's requirements (currently 22.23.4+).

The host needs to support:

- custom CGI executables
- a compatible Bun or Node, or let you install your own
- `mod_cgi` or `mod_cgid`
- `mod_rewrite`
- `Options +ExecCGI` in the webroot
- `.htaccess` with `Options` overrides

`runtimePath` must not contain whitespace.

## CSS and JS

AstralHP supports Astro's usual ways to include CSS and JS, but if you would
prefer a more PHP-style approach, we offer `<CSS>` and `<JS>` components
that keep the source file's URL path, changing the extension when needed,
and add a cachebuster. `<CSS>` serves plain CSS unchanged or compiles SCSS;
`<JS>` bundles JavaScript or TypeScript and its imports for modern browsers.

```astro
---
import { CSS, JS } from "astralhp/components";
---
<CSS src="/style.css" />
<JS src="/js/app.tsx" defer />
```

`<CSS>` renders a `<link rel="stylesheet">` and `<JS>` renders a
`<script src>`. Both add a cachebuster based on hashed contents:

```html
<link rel="stylesheet" href="/style.css?v=0123456789abcdef">
<script type="module" src="/js/app.js?v=0123456789abcdef" defer></script>
```

The source can be absolute (relative to the webroot) or relative to the Astro
component:

```astro
<CSS src="/style/global.css" />
<CSS src="style.css" />
<CSS src="../shared.css" />
```

The resolved file must be inside the webroot. Missing files, existing queries,
fragments, and external URLs are errors.

For a `.ts` or `.tsx` source, `<JS>` changes the rendered extension to `.js`:

```astro
<JS src="script.tsx" />
```

```html
<script type="module" src="/script.js?v=0123456789abcdef"></script>
```

Add `inline` to put the compiled contents directly into a `<style>` or
`<script type="module">`:

```astro
<CSS src="/style.scss" inline />
<JS src="/js/app.ts" inline />
```

## ES3 and Babel

AstralHP supports compiling all the way down to ES3, for ancient browsers.
This approach uses Babel and compiles `import` and `export` to no-ops,
making everything a global.

When doing this, use `<ES3 src="script.tsx" />` for each module you use,
dependencies first. Unlike `<JS>`, there will be no bundling. We'll
scan for `<ES3>` and compile each source file to a `.js` file.

```text
example/
  script.tsx
example/.caches/dist/
  script.js
  script.js.map
```

This Babel configuration is designed to target ancient browsers while
still letting you write code that looks modern. If you don't care about
targeting ancient browsers, you're probably better off using `<JS>`
instead.

If you do care about targeting ancient browsers, keep in mind:

- We use Babel in loose mode, so make sure your code follows best practices
- We assume that all `for...of` is on arrays
- We assume that you only ever use `for...in` on bare objects, not arrays
  or primitives
- You can't use anything that doesn't compile down to ES3, such as
  async/await
- We don't polyfill Map/Set because we have no use for them, either

## Cache directories

The build writes generated Astro files to `example/.caches/dist/`. The live
server serves those generated files alongside static files read directly from
the webroot. Dynamic pages are handled by Astro's Node adapter middleware from
`example/.caches/dist/.server/`. It never copies the webroot's static files.

AstralHP uses a few hidden cache directories:

```text
[project]/
  astralhp.mts
  .caches/
    .astro/
      vite/
  [webroot]/
    .caches/
      dist/
        _astro/
        .server/
```

- `.astro` contains Astro build metadata
- `.astro/vite` contains Vite build metadata
- `dist/_astro` contains Astro runtime dependencies (stuff like styles, scripts, images)
- `dist/.server` contains server software for dynamic pages
- `dist` contains built versions of static pages

AstralHP interprets the project directory as the directory containing
`astralhp.mts` or `package.json`. If neither exists, it uses the webroot.

We recommend not using the same directory for webroot and the project, but you
can do that by setting `webroot: '.'`. This combines the two `.caches/`
directories. With multiple webroots, `.astro` will be in
`.caches/[webroot]/.astro`.

You probably want to add `.caches/` to your `.gitignore`.

Run `npm run build` to compile AstralHP and check its Astro components. Run
