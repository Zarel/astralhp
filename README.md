# AstroHP

AstroHP is intended to make Astro work more like Apache+PHP, with a webroot
containing `.astro` pages and static files.

To run a dev server with `example` as the web root:

```sh
astrohp dev example
```

Files starting with `.astro` are rendered by Astro. Other files are served
statically.

To build and run a live server:

```sh
astrohp build example
astrohp start example
```

The build writes generated Astro files to `example/.caches/dist/`. The live
server serves those generated files alongside static files read directly from
the webroot. Dynamic pages are handled by Astro's Node adapter middleware from
`example/.caches/dist/.server/`. It never copies the webroot's static files.

The live server listens on `127.0.0.1:4321` by default. Set the `HOST` or
`PORT` environment variables to override either value.

## Configuration

While AstroHP can work without a config file, it prefers to have `.astrohp.mts`
in the webroot, or `astrohp.mts` in a parent directory of the webroot:

```ts
export const config: import("astrohp").Config = {
	webroot: "example",
	adapter: "apache-proxy",
	port: 9001,
};
```

In most text editors, you can ctrl+click or cmd+click on "Config" to see
possible config options. If yours doesn't support that, see
`src/config.d.ts` for options.

With a config file in the working directory, commands can omit the directory:

```sh
astrohp dev
astrohp build
astrohp start
```

`astrohp build` and `astrohp start` work with multiple webroots, and can
start one server capable of serving multiple webroots.

## Apache

Set `adapter` to `"apache-proxy"`, then build the site to update AstroHP's
section of the webroot's `.htaccess`:

```sh
astrohp build example
```

If using AstroHP in static mode, this is all you need for shared hosting.
If any pages are dynamic, you'll also need the live server.

The generated block is marked like this, and will be created if it doesn't
exist:

```apache
# ===== BEGIN ASTROHP =====
# Generated by `astrohp build`. EDITS WILL BE OVERWRITTEN.
...
# ===== END ASTROHP =====
```

AstroHP replaces only this block and preserves all configuration outside it.

You can read the block to see what it does (deny access to `.caches`, support
leaving off `.html`, etc).

AstroHP generates a proxy rule for every non-prerendered page. If every page
is prerendered, it generates no proxy rules and Apache is the only server
needed.

The configured `port` is used both when generating the proxy configuration and
starting AstroHP. Apache sends its document root in a private request header so
a shared listener can select the correct webroot, and preserves the original
hostname so Astro sees the public URL. A `PORT` environment variable overrides
the configured port for both commands; when starting multiple `apache-proxy`
webroots, this places all of them on one shared listener:

```sh
PORT=9001 astrohp build example
PORT=9001 astrohp start example
```

The `.htaccess` expects the webroot to be the Apache `DocumentRoot`, Apache
2.4.53 or newer, and `mod_rewrite`. Dynamic pages additionally require
`mod_proxy`, `mod_proxy_http`, and `mod_headers`. The directory must allow
`FileInfo` overrides and either `FollowSymLinks` or `SymLinksIfOwnerMatch`.

(These are all default settings except `FileInfo`, which is the one that allows
`.htaccess` files in the first place, which is usually enabled by shared hosts.)

## CGI on Apache

`apache-cgi` lets you run dynamic pages on shared hosts that don't let you run
a persistent server:

```ts
export const config: import("astrohp").Config = {
	webroot: "www",
	adapter: "apache-cgi",
	// Optional if bun is already on Apache's PATH:
	runtimePath: "/home/username/.bun/bin/bun",
};
```

Compatible with both Node and Bun, although we strongly recommend Bun because
startup times are important if you're going to spawn a new process on every
pageview.

Use a Node version that meets AstroHP's requirements (currently 22.18+).

The host needs to support:
- custom CGI executables
- a compatible Bun or Node, or let you install your own
- `mod_cgi` or `mod_cgid`
- `mod_rewrite`
- `Options +ExecCGI` in the webroot
- `.htaccess` with `Options` overrides

`runtimePath` must not contain whitespace.

## Components

AstroHP supports Astro's usual ways to include CSS and JS, but if you would
prefer a more PHP-style approach, we offer `<CSS>` and `<JS>` components
that cachebust an asset while leaving it unmodified and in the same location.

```astro
---
import { CSS, JS } from "astrohp/components";
---
<CSS src="/style.css" />
<JS src="/js/app.tsx" defer />
```

`<CSS>` renders a `<link rel="stylesheet">` and `<JS>` renders an inline
`<script src>`. Both forward additional attributes and append the local file's
modification time encoded in base 36:

```html
<link rel="stylesheet" href="/style.css?loyw3v28">
<script src="/js/app.js?loyw3v28" defer></script>
```

The source can be root-relative or relative to the rendered page:

```astro
<CSS src="/style/global.css" />
<CSS src="style.css" />
<CSS src="../shared.css" />
```

The resolved file must be inside the webroot. Missing files, existing queries,
fragments, and external URLs are errors.

For a `.ts` or `.tsx` source, `<JS>` changes the rendered extension to `.js`:

```astro
<JS src="script.tsx" />
```

```html
<script src="script.js?loyw3v28"></script>
```

## Babel

AstroHP recursively compiles every `.ts` and `.tsx` file in the webroot,
excluding `.d.ts` files and private directories, hardcoded to use
Showdown's Babel configuration.

```text
example/
  script.tsx
example/.caches/dist/
  script.js
  script.js.map
```

This Babel configuration is designed to target ancient browsers while
still letting you write code that looks modern. If you don't care about
targeting ancient browsers, you're probably better off using Astro's
built-in TypeScript support instead.

If you do care about targeting ancient browsers, keep in mind:

- We use Babel in loose mode, so make sure your code follows best practices
- We assume that all `for...of` is on arrays
- We assume that you only ever use `for...in` on bare objects, not arrays
  or primitives
- You can't use anything that doesn't compile down to ES3, such as
  async/await
- We don't polyfill Map/Set because we have no use for them, either

`astrohp build` compiles all directory targets after Astro renders the pages.
`astrohp dev` performs an initial compilation, watches source files through
Vite, recompiles the changed file, and reloads the page. Raw `.ts` and `.tsx`
files are never served.

## Cache directories

Each webroot contains one hidden cache directory:

```text
.caches/
  .astro/
    vite/
  dist/
```

You probably want to add `.caches/` to your `.gitignore`.

## Developing AstroHP

Run `npm run build` to compile AstroHP and check its Astro components. Run
`npm test` for the full test suite.
